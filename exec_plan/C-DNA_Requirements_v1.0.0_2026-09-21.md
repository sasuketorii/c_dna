## 0. 文書の読み方と実装上の契約

### 0.1 要件の強さ

- **MUST／P0**：対象リリースの必須要件。未完了のまま「完成」と報告しない。
- **SHOULD／P1**：推奨要件。実装しない場合は、理由・影響・代替を記録する。
- **MAY／P2**：拡張候補。P0の完成を遅らせてまで実装しない。
- **研究ゲート**：改善効果を実測してから採用する項目。候補の実装・評価は必須でも、劣るモデルの本番採用は必須ではない。
- **製品目標値**：本書で置く受け入れ目標。実測済みの性能ではない。

要件IDは `REQ-<領域>-<番号>`、受け入れ試験IDは `AT-<番号>` とする。要件を削る場合は、本書との差分・理由・承認者を残す。

### 0.2 情報の区別

本書では次を混同しない。

| 種類 | 取り扱い |
|---|---|
| ユーザーの要求 | C-DNA、判断学習、MCP、四択、備考、左右スワイプ、Python 3.14付近、Rust／Mojo活用、秘匿した改善共有、性格傾向 |
| 本書の採用判断 | ローカルファースト、macOS先行、学習と推論の分離、候補比較モデル、明示承認付きモデル更新 |
| 公式資料で確認した事実 | 出典番号 `[Sxx]` を付け、末尾に公式URL・確認内容を記載 |
| 未検証事項 | OS別の依存関係一式、実データ精度、実機速度、商用利用許諾など。試験・確認ゲートを設ける |

### 0.3 完成の意味

<a id="req-gov-001"></a>

**REQ-GOV-001／P0**：動く画面だけ、モックだけ、学習ノートブックだけ、MCPツール一覧だけで完了しない。取り込み→確認→学習→推論→訂正→再学習→削除→復元までを製品として完結させる。

<a id="req-gov-002"></a>

**REQ-GOV-002／P0**：安全性・プライバシー・データ整合性の失敗を、平均精度や平均速度で相殺しない。

<a id="req-gov-003"></a>

**REQ-GOV-003／P0**：精度目標が未達なら、実測値と利用可能な範囲を表示する。モデルの採用条件を下げて「高精度を達成」と報告しない。

<a id="req-gov-004"></a>

**REQ-GOV-004／P0**：実装・試験・実機確認・契約確認を分けて報告する。権利者の許諾、署名証明書、本人データを入手したことにしない。

## 1. プロダクト定義

### 1.1 一文での定義

**C-DNAは、経営者の判断事例・明示方針・例外条件を日常業務と短いヒアリングから蓄積し、現在の背景に対する候補の選好を高速に推定する、個人所有の意思決定学習基盤である。**

経営者の人格、能力、意識、遺伝情報を複製するものではない。「DNA」は判断特性を表す製品上の比喩として扱う。

### 1.2 主な利用者

| 利用者 | 実現したいこと |
|---|---|
| 経営者本人 | 過去の説明を繰り返さず、自分の基準をAIに使わせる。短時間で不足領域を育てる |
| 経営者が許可したAIエージェント | 判断方針・類似事例・不足情報を取得し、実際の判断を記録候補として返す |
| 経営者が許可した業務アプリ | 案件・タスク・企画等の候補を、定義された権限内で比較する |
| 開発・運営者 | 本文を受け取らず、速度・失敗率・負担に関する許可された診断指標から改善案を作る |

初期版に、社員全員の人事評価、他人の非同意プロファイリング、組織横断の統一人格モデルを持ち込まない。

### 1.3 中心となる価値

1. **説明の再利用**：一度承認した基準を、複数のAI・アプリで再利用できる。
2. **少ない手間での学習**：不足している条件だけを、四択・比較・備考で聞く。
3. **構造化後の高速判断**：長文理解と小型モデルの採点を分離する。
4. **根拠の確認可能性**：本人の明示発言、過去の選択、モデルの推測を見分けられる。
5. **本人の所有と撤回**：訂正、無効化、削除、バックアップ、出力を本人が制御できる。

### 1.4 避けるべき設計

<a id="req-prd-001"></a>

**REQ-PRD-001／P0**：以下を禁止する。

- 「Pythonだから正確」「Mojoだから正確」と説明する。
- 本人の選択を当てたことと、選択が経営成果を最大化したことを同一視する。
- 「一万件入れれば必ず本人を再現」「必ず本人を超える」と保証する。
- AIの提案・要約・推測を本人の実際の選択として扱う。
- スワイプ数・連続利用日数を精度に変換する。
- 推論結果を本人の署名・承認・契約意思表示として使う。

## 2. リリース範囲と対象環境

### 2.1 初回正式版R1に含めるもの

| 領域 | R1の完成条件 |
|---|---|
| アプリ | macOS上でインストール・起動・ロック・更新・バックアップ・復元できる |
| 初期取り込み | 要約貼り付け、C-DNA JSON、ChatGPT／Claudeの対応済みエクスポート形式 |
| 判断管理 | 候補確認、訂正、出典、時点、実例／仮想の区別、削除 |
| 学習体験 | 四択、二案比較、単一案の許容性、備考、判断逆転条件、取り消し |
| 能動学習 | 不足領域・不確かさ・実務重要性から質問を選び、偏りを抑える |
| モデル | 即時記憶、線形比較学習、LightGBM比較実験、本番モデル管理 |
| 推論 | 候補順位、方針適合、根拠、不足情報、適用外、保留 |

「LightGBMやMojoが線形Rustモデルより優れていること」は完成条件にしない。**優劣を正しく測り、最も適した構成を選べること**を完成条件にする。

### 2.2 後続範囲

**P1**：Windows 11 x64正式対応、追加埋め込みモデル、ユーザーによる短い音声回答の取り込み、業務アプリの個別アダプター。

**P2**：Linux GUI、複数端末自動同期、組織共通モデル、連合学習、専門家モデル市場、巨大LLMの個人別微調整、成果を直接最大化するオンライン方策。

次はR1の対象外：独自チャット基盤の全面置換、ブラウザーの会話自動スクレイピング、他社セッションCookieの取得、キーロガー、無断の会話常時収集、金融取引・契約・人事措置の自動実行。

### 2.3 対象OS・ハードウェア

<a id="req-env-001"></a>

**REQ-ENV-001／P0**：正式版の最初の基準機は、Apple Silicon搭載Mac、メモリ16GB、macOS 14以上のうち検証済みのバージョンとする。最古対応OSと現行安定OSを別々に検証する。実際の対応OS一覧はリリース成果物に固定する。

<a id="req-env-002"></a>

**REQ-ENV-002／P0**：GPU・Mojo・Python開発環境・Node.jsをユーザーに手動インストールさせない。標準推論はCPUだけで機能する。

<a id="req-env-003"></a>

**REQ-ENV-003／P0**：Python学習ランタイムはアプリ管理の署名・ハッシュ検証済みパッケージとして配布する。ダウンロード型の場合は、容量と必要性を事前表示し、中断再開に対応する。

<a id="req-env-004"></a>

**REQ-ENV-004／P0**：Mojoのサポート範囲とアプリのサポート範囲を分離する。公式案内ではMojoはMac／Linuxをネイティブに扱い、WindowsではWSLを案内しているため、Windows製品にWSLを必須化しない。[S10](#source-s10)

<a id="req-env-005"></a>

**REQ-ENV-005／P0**：ネットワークがない状態でも、保存済み質問への回答、判断履歴、承認済み方針、ローカル学習、導入済みモデルの推論が利用できる。新規のクラウド質問生成・クラウド抽出は利用不可と明示する。

## 3. 判断データの六層と三つの出力モード

### 3.1 六層

| 層 | 内容 | 更新主体 | 学習での扱い |
|---|---|---|---|
| 性格傾向 | Big Five等の尺度結果 | 本人／許可された測定 | 初期版では説明・ヒアリング補助。既定でスコアラーへ投入しない |
| 価値観 | 成長、利益、時間、信用等の優先 | 本人 | 仮説・明示選好。実際の選択と区別 |
| 明示方針 | 禁止、承認条件、優先順位 | 本人の明示承認 | バージョン付きルール |
| 状況 | 目的、予算、納期、人数等 | 入力元＋本人確認 | 判断時点の特徴量 |
| 判断観測 | 実際の選択、比較、保留 | 本人／出典付き記録 | 適格性に従って学習 |
| 結果 | 受注、工数、利益、後悔等 | 後日の記録 | 別モデル・別評価。過去の入力へ逆流させない |

<a id="req-dom-001"></a>

**REQ-DOM-001／P0**：性格、価値観、状況、行動、成果を同一のJSONテキストに埋め込んで正本にしない。独立した型・履歴を持つ。

### 3.2 出力モード

| モード | 問い | 出力の意味 |
|---|---|---|
| `imitate` | この背景で、本人はどの候補を好みそうか | 本人の選好の推定。正解や承認ではない |
| `policy_check` | 現在の承認済み方針に候補が合うか | 明示ルールへの適合・違反・判定不能 |
| `advisor` | 本人の方針を尊重しつつ、別の観点がないか | 補助的な提案。本人再現とラベルを分ける |

<a id="req-dom-002"></a>

**REQ-DOM-002／P0**：画面・API・ログ・評価でモードを明示する。モード間のスコアを混ぜない。

<a id="req-dom-003"></a>

**REQ-DOM-003／P0**：`imitate`でも方針違反の候補を「実行してよい」としない。ランキングは方針状態を併記し、実行権限は常に `none` とする。

<a id="req-dom-004"></a>

**REQ-DOM-004／P0**：新たなルール、本人の同意、モデル本番昇格、外部送信の許可を、LLMの文面だけで確定しない。

### 3.3 状況のスコープ

全記録は `vault_id`、`owner_id`、任意の `org_id`、`workspace_id`、`domain` を持つ。複数会社・複数事業の判断を、無条件に相互利用しない。

本人モデルであっても、「個人としての好み」「会社Aの方針」「会社Bの機密」は別スコープとする。R1は単一オーナー・複数ワークスペースを扱い、複数オーナー共同学習は対象外とする。

## 4. 代表ユーザージャーニー

### 4.1 最初の起動

1. アプリを起動する。
2. ローカル保管庫を作成し、復元方法・鍵の保管方針を確認する。
3. 会社名は任意。事業領域、よく判断するテーマ、本人が避けたいテーマを設定する。
4. 「要約を貼り付ける」「会話ファイルを読み込む」「すぐ質問に答える」から選ぶ。
5. 取り込んだ仮説を少数ずつ確認する。
6. 最初の背景付き質問に回答する。
7. 「覚えたこと」「まだ分からないこと」「接続できるAI」を表示する。

<a id="req-ux-001"></a>

**REQ-UX-001／P0**：外部アカウント認証、性格診断、全文履歴インポート、診断情報共有を初期利用の必須条件にしない。

### 4.2 日常業務から育てる

```text
経営者がCodex／Claude Codeとの会話で判断
  → エージェントがC-DNAへ「判断候補」を登録
  → アプリの確認待ちへ届く
  → 本人が確認・条件を追記
  → 記憶へ即時反映
  → 軽量モデルの更新候補を作成
  → 独立評価／本人による本番昇格承認に従って利用
```

同じ会話の取得を何度も繰り返さない。エージェントは「本人が実際に決めた」と分かる箇所だけを提案し、曖昧な相づちは採択扱いしない。

### 4.3 四択で育てる

```text
C-DNAが学習不足を検出
  → 質問テンプレート／接続エージェントが背景と四択を作る
  → スキーマ・重複・誘導性を確認
  → 本人が1〜4で回答
  → 任意の備考・逆転条件を記入
  → 観測と新たな仮説を分離して保存
```

### 4.4 判断を使う

```text
業務アプリ／エージェントが背景＋候補を渡す
  → スコープ・許可・入力完全性を確認
  → 明示ルールを評価
  → 小型モデルが候補を採点
  → 似た事例と相違点を検索
  → 順位・根拠・不確かさ・不足情報を返す
  → 実際の意思決定は本人または外部の正式承認フロー
```

### 4.5 間違えたとき

本人は「選択が違う」「前提が違う」「方針が変わった」「そもそも判断できない」を区別して訂正できる。元の予測を上書きせず、予測→本人の訂正→採用された学習データを追跡できる。

## 5. 画面構成とUI要件

### 5.1 情報設計

| 画面 | 主目的 | 必須の状態 |
|---|---|---|
| ホーム | 今日の確認・学習不足・更新状態 | 未設定／通常／保管庫ロック／学習停止 |
| 育てる | 四択・比較・許容性・備考 | 準備中／質問あり／候補不足／オフライン／保存失敗 |
| 判断する | 背景と候補を入力して使う | 下書き／解析待ち／情報不足／結果／保留 |
| 判断の記憶 | 過去の判断を検索・訂正 | 出典あり／出典なし／確認待ち／削除処理中 |
| 判断方針 | 承認済み方針と仮説を区別 | 未承認／有効／期限切れ／競合 |
| 学習マップ | 領域ごとの記録・検証状態 | 未学習／記録あり未検証／検証中／検証済み |

### 6.1 取り込み経路

| 経路 | 入力 | 初期の信頼状態 |

| 要約貼り付け | ChatGPT／Claudeが出した人物・判断の要約 | 未確認の仮説 |

### 6.2 要約取り込み用の標準プロンプト

アプリは以下の日本語プロンプトをコピーできるようにする。

```text
C-DNAに取り込むため、私の経営判断の傾向を整理してください。
現在あなたが実際に参照できる会話・情報だけを根拠にしてください。
参照できない過去の会話を見たことにしたり、根拠を創作しないでください。

次を分けてください。
1. 私が実際に決めたこと
2. 私が明示した方針
3. 私が理想として述べただけのこと
4. あなたの推測
5. 情報がなく分からない領域

各項目に、分かる範囲で以下を含めてください。
判断領域／当時の状況／比較した候補／選択／本人が明示した理由／
判断が逆転する条件／本人の根拠発言／時期／確実な点と推測の区別。

あなた自身が提案しただけの内容を、私が採用したことにしないでください。
会話IDや引用元が見えない場合は「参照できない」としてください。

```

### 7.3 状況・選択肢・回答の例

以下は架空の業務例である。IDは可読性のため短縮しており、本番では正式IDを使う。

```json
{
  "schema_version": "1.0",
  "case_id": "case-example-001",
  "workspace_id": "workspace-example",
  "domain": "product_delivery",
  "case_kind": "hypothetical",
  "context": {
    "as_of": "2026-09-21T10:00:00Z",
    "objective": "既存顧客への影響を抑えながら新機能を公開する",
    "facts": [
      {"key": "engineering_capacity", "value": "small_team", "evidence_status": "explicit"},
      {"key": "customer_impact", "value": "unknown", "evidence_status": "unknown"}
    ],
    "constraints": [],
    "missing_fields": ["customer_impact_severity", "new_feature_commitment"]
  },
  "candidates": [
    {"candidate_id": "opt-fix", "description": "不具合改善を先に完了する"},
    {"candidate_id": "opt-feature", "description": "新機能を優先する"},
    {"candidate_id": "opt-parallel", "description": "両方を並行する"},
    {"candidate_id": "opt-investigate", "description": "顧客影響と契約条件を確認してから決める"}
  ],
  "observation": {
    "response_type": "choose_one",
    "selected_candidate_ids": ["opt-investigate"],
    "rationale_explicit": "重大度と契約上の約束が分からないと決められない",
    "reversal_conditions": [],
    "origin": "human_app",

  }
}
```

**重要**：この例はアプリが保存する完成済みレコードの形であり、外部MCPの入力ではない。外部クライアントは `verification_state`、`confirmed_at`、`confirmed_by` を設定できない。

### 7.4 回答型

| response_type | 意味 | 学習への変換 |
|---|---|---|
| `choose_one` | 提示候補から一つ選択 | 選択候補と比較済み候補の選好制約 |
| `choose_set` | 複数が許容される | 許容集合。自動的に集合内の順位を作らない |
| `pairwise` | 二案の比較 | left/right/tie/insufficient |
| `acceptability` | 単一案の許容 | accept/reject/conditional/insufficient |
| `need_information` | 背景が不足 | 不足項目学習。候補の敗北ラベルにしない |
| `none_fit` | 候補が適切でない | 候補生成の改善対象。自動で全候補の絶対拒否へ変換しない |
| `skip` | 今は答えない | 学習ラベルにしない |
| `defer` | 意思決定として保留 | 状況依存の実際の選択として保存 |

「追加調査を選ぶ候補」と、アプリへの「情報不足」という応答は別である。前者は業務上の行動、後者は提示問題の不十分さを示す。

### 7.5 観測の信頼区分

| 区分 | 選好モデルへの既定利用 |
|---|---|
| アプリ内で本人が回答した実判断 | 利用可能 |
| 出典を本人が確認した実判断 | 利用可能 |
| 本人が回答した仮想問題 | 利用可能。ただし実判断と別集計・重みを記録 |
| 本人が確認した価値観の文章 | 直接の選択ラベルにはしない |
| アシスタントが推定した人物像 | 学習しない。確認用仮説のみ |
| エージェントが提出した未確認記録 | 学習しない |
| AIが生成した回答 | 本人ラベルにはしない |
| 合成した状況と本人の回答 | 仮想問題として利用。実例として数えない |

## 9. 能動学習と質問生成

### 9.1 初期の判断領域

R1は以下の六領域を初期分類として採用する。会社固有の下位タグは追加できる。

| domain | 含める判断 |
|---|---|
| `resource_allocation` | 時間・予算・人員の配分 |
| `product_delivery` | 品質・納期・機能・技術負債 |
| `customer_commercial` | 価格・受注条件・継続対応・顧客優先順位 |
| `organization_delegation` | 内製／外注・権限委譲・確認の深さ |
| `growth_strategy` | 集中／分散・検証／拡大・撤退条件 |
| `risk_reputation` | 損失許容・不可逆性・信用・対外影響 |

個人の性格尺度の結果はこの分類に混ぜない。人の採否・待遇など重大な判断の自動化はR1の対象外とし、組織設計の一般的選好に範囲を限る。

### 9.2 学習不足の表現

`LearningGap` は以下を含む。

```text
id / domain / context_region / evidence_count / independent_case_count
real_vs_hypothetical_breakdown / uncertainty_reason / business_importance
missing_conditions / proposed_question_type / estimated_answer_burden
last_asked_at / cooldown_until / excluded_by_owner
```

<a id="req-al-001"></a>

**REQ-AL-001／P0**：単純な件数不足、選択の競合、未知条件、時間的変化、入力情報の欠損を、別の不足理由として返す。

<a id="req-al-002"></a>

**REQ-AL-002／P0**：確率校正前のモデルの出力を、正確な「自信」として質問選定に使わない。順位差・モデル間の不一致・事例密度は別の信号として保持する。

### 9.3 質問の優先度

初期の選定関数は次の構造を持つ。係数は固定設定として版管理し、学習で自由に変更しない。

```text
priority(q)
  = weighted_sum(
      uncertainty,
      domain_gap,
      owner_declared_importance,
      expected_frequency,
      contradiction_to_clarify,
      temporal_drift_signal
    )
    - answer_burden
    - repetition_penalty
```

これはC-DNAの設計ヒューリスティックであり、最適な情報獲得を保証する数式ではない。

<a id="req-al-003"></a>

**REQ-AL-003／P0**：重要度・出現頻度が不明なら「不明」とする。本人が宣言した重要度と、実際の利用ログから観測した頻度を区別する。

<a id="req-al-004"></a>

**REQ-AL-004／P0**：同一のケースファミリーを連続で出しすぎない。ユーザーが領域を固定した場合を除き、セッションの偏りを抑える。

### 9.4 質問配分の初期設定

長期的な目安として、学習不足・不一致50%、実務分布からの代表問題30%、新しい条件の探索20%とする。これは初期の製品設定で、性能保証ではない。

独立評価用の問題は、この質問最適化とは別のスケジューラーが抽出する。評価問題の正解を見ながら質問を最適化しない。

<a id="req-al-005"></a>

**REQ-AL-005／P0**：選定元、候補プール、選定方針版、ランダムseed、分かる場合の選定確率を記録する。後から選定確率を作らない。

### 9.5 質問生成の責務分離

```text
GapDetector            何を学ぶかを決める
QuestionPlanner        必要な条件と変化させる軸を定義する
QuestionGenerator      テンプレート／LLMで文章化する
QuestionValidator      型・重複・誘導・実例偽装を検査する
QuestionScheduler      負担と多様性を考慮して提示する
AnswerInterpreter      本人の回答を型付き観測にする
```

<a id="req-al-006"></a>

**REQ-AL-006／P0**：LLMが生成した質問には `synthetic_scenario=true` を付ける。本人の実際の会社で起きた出来事のように書かない。

<a id="req-al-007"></a>

**REQ-AL-007／P0**：四択を無理に作って内容を劣化させない。意味のある四択を作れない場合は、二案比較または不足条件の質問へ切り替える。

<a id="req-al-008"></a>

**REQ-AL-008／P0**：候補に、極端に望ましくない案、道徳的に一方だけよく見える表現、長さの過度な差、特定候補だけの追加根拠を避ける。検査に失敗した問いは再生成または隔離する。

<a id="req-al-009"></a>

**REQ-AL-009／P0**：判断が逆転する条件を尋ねるときは、原則として一度に一つの条件を変える。複数変更した場合は変数を明示する。

### 9.6 備考からの追加学習

備考は三つに分ける。

1. 今の回答の理由：`rationale_explicit`。
2. 今回の背景に足りなかった事実：確認後に新しい状況版へ追加。
3. 一般化できそうな方針：未承認の `Principle` 候補。

<a id="req-al-010"></a>

**REQ-AL-010／P0**：LLMが備考から推測した条件を、本人が言った条件にしない。曖昧な場合は「この意味で合っていますか」と確認する。

<a id="req-al-011"></a>

**REQ-AL-011／P0**：「回答後の理由」を同じ問題の入力特徴に使わない。答えを含む理由から答えを予測する、見せかけの精度向上を防ぐ。

### 9.7 人間の一貫性と変化

繰り返し質問は、記憶力テストや罰として行わない。本人の負担が小さい範囲で、時間を空けた確認に利用する。

<a id="req-al-012"></a>

**REQ-AL-012／P0**：以前と回答が違ったときは、誤操作・背景差・方針変化・同程度の選好を確認する。回答の変化を自動的に低品質扱いしない。

## 10. 学習アルゴリズム

### 10.1 学習する関数

四択のA/B/C/Dを固定クラスとして学習しない。

```text
s = fθ(context, candidate, optional_candidate_set_features)
```

`context` は判断時点の背景、`candidate` は候補の内容、`candidate_set_features` は比較集合の必要な特徴である。候補位置・表示ラベルは学習特徴にしない。

### 10.2 最初のモデル：対称なペア比較

初期モデルは、特徴表現 `φ(x,a)` を用いた線形スコアとする。

```text
score(x, a) = w · φ(x, a)
P(a ≻ b | x) = sigmoid(w · (φ(x,a) - φ(x,b)))
```

この確率は二案比較モデルの出力であり、四択における選択確率や「経営上正しい確率」ではない。

<a id="req-ml-001"></a>

**REQ-ML-001／P0**：scikit-learnの `SGDClassifier(loss="log_loss", fit_intercept=False)` を初期候補とする。`partial_fit` による逐次更新を使える。[S20](#source-s20)

<a id="req-ml-002"></a>

**REQ-ML-002／P0**：一方向の正例だけを渡さない。比較 `(a,b,1)` に対して符号を反転した `(b,a,0)` を対で生成するか、同等の対称性を保証する。`classes=[0,1]` を初回に指定する。

<a id="req-ml-003"></a>

**REQ-ML-003／P0**：四択で一つ選ばれた場合、本人が比較した他候補との制約を作る。ただし一件から生成した複数ペアの重み合計を、その一件の重みに正規化する。反転ペアにも二重の重みを付けない。

例えば、一件の重みが `w_case`、比較がk個なら、正方向・反転方向の各ペアの重みは原則 `w_case/(2k)` とする。

<a id="req-ml-004"></a>

**REQ-ML-004／P0**：非選択候補間の順位を作らない。候補未提示の実判断から、架空の負例を自動生成しない。

<a id="req-ml-005"></a>

**REQ-ML-005／P0**：tieを無理に二値分類しない。初期版では順位ペアから除外し、同程度を返す閾値の校正・専用評価に利用する。tie対応損失へ進む場合は別モデル版とする。

### 10.3 文脈が消える問題を防ぐ

`φ(x,a)=context_features(x)+candidate_features(a)` の単純加算だけでは、差分で背景項が消える。そのため次を明示的に表現する。

- 納期の厳しさ×外注の短納期性。
- 社内資産化の重要度×内製の継続性。
- 損失許容×取り返しのつかなさ。
- 顧客影響×変更速度。
- 予算制約×候補費用。

<a id="req-ml-006"></a>

**REQ-ML-006／P0**：背景と候補の相互作用を特徴量定義に含める。背景だけを変えた契約試験で、設計上変わるべき候補差が変わることを確認する。

### 10.4 特徴量の初期設計

| 群 | 主な項目 |
|---|---|
| 背景 | domain、目的種別、時間制約、事業段階、資源制約、不可逆性 |
| 候補 | コスト帯、必要工数、納期への影響、再利用性、顧客影響、可逆性 |
| 相互作用 | 背景×候補の許可された組み合わせ |
| 欠損 | 値が未知か、根拠が推測か |
| 文章 | 検証済み埋め込み・語彙表現。任意の追加プロファイル |

<a id="req-ml-007"></a>

**REQ-ML-007／P0**：初期の特徴量スキーマは小さく固定する。高次元の全組み合わせを自動で追加しない。

<a id="req-ml-008"></a>

**REQ-ML-008／P0**：人名、会社名、候補ID、会話ID、表示位置、答え、回答後の理由、後日の成果をショートカット特徴量として使わない。

<a id="req-ml-009"></a>

**REQ-ML-009／P0**：標準化・欠損処理・カテゴリ辞書は学習側だけでfitし、推論側に同じ値を配布する。逐次学習中に標準化だけを変更して、重みの意味を壊さない。

<a id="req-ml-010"></a>

**REQ-ML-010／P0**：新しい特徴量版は旧モデルへ投入できない。変更時は対象モデルを再学習し、並行評価する。

### 10.5 単一案の許容性

`acceptability` はペア選好と別のタスクとする。「AはBよりよい」から「Aを承認する」を推論しない。

初期は許可された特徴量に対する二値／条件付き分類、または明示記憶として実装する。許容モデルの校正と評価は選好モデルと分離する。

<a id="req-ml-011"></a>

**REQ-ML-011／P0**：許容性の `conditional` は、その条件を構造化して確認する。条件を削ったacceptラベルにしない。

### 10.6 第二候補：LightGBM

LightGBMのランキングAPIを用い、一つの判断場面を一つのgroupとして扱う。[S22](#source-s22)

初期探索範囲の例：`num_leaves` は7／15／31、深さは小さく制限し、葉の最小データ数・正則化・木の本数を少数の設定で比較する。これらは調査実験の候補で、最適値ではない。

<a id="req-ml-012"></a>

**REQ-ML-012／P0**：`choose_one` をone-positive rankingにする場合、非選択候補は「その集合で選ばれなかった」ことを表す。絶対的な拒否と説明しない。

<a id="req-ml-013"></a>

**REQ-ML-013／P0**：学習・評価・校正をケースファミリー単位で分ける。groupを行単位に解体してランダム分割しない。

<a id="req-ml-014"></a>

**REQ-ML-014／P0**：LightGBMのスコアはそのまま確率表示しない。線形モデルを上回る実測結果がなければ本番へ昇格させない。

### 10.7 第三候補：小型ニューラルモデル

PyTorchによる小型MLPはP1研究候補とする。構造化特徴＋固定文章表現を入力し、本人ごとの学習部分を小さく保つ。[S16](#source-s16)

条件：線形／木モデルでは解けない失敗パターンが実データで見え、必要なデータと配布可能な推論形式が揃うこと。

<a id="req-ml-015"></a>

**REQ-ML-015／P0**：R1の完成のために巨大モデルの微調整を必須にしない。少量データで本人の能力を丸ごと学んだと説明しない。

### 10.8 データ重み

重みは、本人確認、実例／仮想、時点、ケース重複、訂正状態に依存する。重み設定は学習manifestに保存する。

<a id="req-ml-016"></a>

**REQ-ML-016／P0**：AIが出した「確信度」をそのまま教師データの重みにしない。品質判定は出典・確認状態を主とする。

<a id="req-ml-017"></a>

**REQ-ML-017／P0**：古い実判断を自動で無価値にしない。方針の有効期間を優先し、時間減衰を使う場合は比較実験を行う。

<a id="req-ml-018"></a>

**REQ-ML-018／P0**：件数の多い一領域に全体が支配されないよう、領域ごとの評価を必須にする。重みの調整は検証対象とする。

### 10.9 三段階の更新

| 段階 | 動作 | 本番への反映 |
|---|---|---|
| 記憶更新 | 確認済み観測を保存・検索可能にする | 即時。一般化せず事例として扱う |
| 軽量モデル更新 | 小型比較モデルの新候補を作る | 内部評価・質問選定に使用。外部予測は昇格方針に従う |
| バッチ再学習 | 学習snapshotから再学習・校正・比較 | 承認後に切り替える |

<a id="req-ml-019"></a>

**REQ-ML-019／P0**：新回答が来ても毎回全学習を実行しない。短いdebounce、同じsnapshotの重複排除、一つの保管庫に同時一学習を基本とする。

<a id="req-ml-020"></a>

**REQ-ML-020／P0**：逐次更新モデルは「暫定」と識別する。過去モデルの校正を、新しい重みにそのまま有効として付けない。

<a id="req-ml-021"></a>

**REQ-ML-021／P0**：訂正・削除は追加学習だけでは相殺しない。汚染されたモデルを隔離し、適格データのsnapshotから再学習する。

### 10.10 オンライン評価

実務で新しい判断が届く場合、学習前に予測を保存し、後から本人回答と比較する `predict-then-update` を採用する。

<a id="req-ml-022"></a>

**REQ-ML-022／P0**：本人がモデルの答えを見てから選んだ場合は `model_exposure=true` とし、独立した本人一致率の主評価に混ぜない。

## 11. 不確かさ・保留・根拠

### 11.1 確率とスコア

確率校正は、モデル出力と実際の頻度の関係を独立データで確認する工程である。単にsoftmaxを掛けても校正済みとはならない。[S21](#source-s21)

<a id="req-unc-001"></a>

**REQ-UNC-001／P0**：出力は `raw_score`、`pairwise_probability`、`top_choice_agreement_estimate` を区別し、未検証項目はnullにする。

<a id="req-unc-002"></a>

**REQ-UNC-002／P0**：二案比較の確率を四択確率へ自動転用しない。候補数・候補集合が違う場合の校正適用範囲を保存する。

<a id="req-unc-003"></a>

**REQ-UNC-003／P0**：校正用データと、最終結果を報告するテストデータを分ける。少量データでは校正できないことを許容し、未校正表示にする。

### 11.2 保留理由

最低限、以下のenumを実装する。

```text
INSUFFICIENT_CONTEXT
LOW_EVIDENCE
UNCALIBRATED_MODEL
OUT_OF_DISTRIBUTION
CLOSE_CANDIDATES
CONFLICTING_PRINCIPLES
MODEL_UNAVAILABLE
MODEL_INVALIDATED
UNSUPPORTED_DOMAIN
SCOPE_DENIED
```

<a id="req-unc-004"></a>

**REQ-UNC-004／P0**：自信が低いこと、入力不足、ルール衝突、権限不足を同じ「分かりません」に潰さない。

<a id="req-unc-005"></a>

**REQ-UNC-005／P0**：低スコア差だけを未知領域検出としない。欠損、許可範囲、事例距離、領域、モデル適用期間を併用する。

<a id="req-unc-006"></a>

**REQ-UNC-006／P0**：候補が全て不適切な場合に、その中の最上位を無条件に推薦しない。必要に応じて候補の作り直しを返す。

### 11.3 根拠の三分類

| 種類 | 表示 |
|---|---|
| 明示ルール | 「あなたが承認した方針」＋対象版 |
| 過去事例 | 「似た状況での判断」＋相違点 |
| モデル推定 | 「記録からの推定」＋未検証部分 |

<a id="req-unc-007"></a>

**REQ-ARC-005／P0**：`open_path`、`execute_shell`、任意URLのfetch等を汎用コマンドとして公開しない。特定用途の引数検証済みcommandに分ける。

### 12.3 Pythonワーカー

Pythonは学習・評価・データ変換に使用する。通常の画面操作や学習済み線形モデルの推論のために、常時Pythonサーバーを起動しない。

| 項目 | 要件 |
|---|---|
| 起動 | 必要時にRustがバージョン固定された学習ワーカーを起動 |
| 通信 | 長さ上限付きフレームの標準入出力。ログは別経路。学習本文を標準ログに出さない |
| データ受け渡し | 許可・適格性確認済みsnapshotをバッチで渡す。保管庫のマスターキーを渡さない |
| 並列実行 | 保管庫ごとに学習一件。CPU・メモリの予算を設定 |
| 一時保存 | 原則メモリ内。必要な場合は暗号化されたワーク領域。平文のtemp/Parquetへ自動spillしない |
| キャンセル | cooperative cancelの後、期限超過時は当該プロセスグループを終了 |
| クラッシュ | 本番モデルを維持。候補出力は未検証のまま隔離 |
| 再現 | Python版、lock hash、seed、特徴量版、snapshot ID、学習設定を保存 |

<a id="req-arc-006"></a>

**REQ-ARC-006／P0**：学習プロセスを終了しても、確定済み観測や現行モデルを壊さない。ジョブとモデル昇格をトランザクション境界で分ける。

<a id="req-arc-007"></a>

**REQ-ARC-007／P0**：初期版のためにFastAPI、Celery、Redis、分散キュー、Kubernetesを必須にしない。単一端末で必要な処理を完結させる。

<a id="req-arc-008"></a>

**REQ-ARC-008／P0**：Pythonは通常のCPython 3.14系を基準とする。free-threaded版、実験的JIT、GPU必須構成は別の評価対象とする。

### 12.4 データ境界・通信方式

| 境界 | 方式 | 主な防御 |
|---|---|---|
| UI → Rust | 型付きTauri command | allowlist、schema、workspace照合 |
| Rust → Python | ローカル子プロセスのフレーム通信 | payload上限、ジョブ認証、期限、削除epoch |
| MCP bridge → Rust | macOSのローカルソケット | ユーザー専用権限、接続ペアリング、保管庫状態 |
| Rust → 推論エンジン | 型付き数値入力 | モデル・特徴量版、finiteチェック、配列長 |
| Rust → 外部AI | provider adapter | 明示同意、送信プレビュー、スコープ、上限 |
| Rust → 診断受信API | HTTPSの固定schema | 本文禁止、未知フィールド拒否、送信前検証 |

<a id="req-arc-009"></a>

**REQ-ARC-009／P0**：MCP接続のために既定でTCPポートを開かない。アプリ終了時・保管庫ロック時は、外部ツールへロック状態を返す。

<a id="req-arc-010"></a>

**REQ-ARC-010／P1**：WindowsではNamed Pipe等の同等のローカル認証IPCを採用する。macOSのソケットパス・Keychainの実装をドメイン層へ混ぜない。

<a id="req-arc-011"></a>

**REQ-ARC-011／P0**：ローカルで動くクライアントだから信頼済み、とは扱わない。クライアントごとの権限とペアリングを必要とする。

### 12.5 ジョブの共通状態

```text
queued → running → validating → succeeded
                  ├──────────→ failed
                  └──────────→ cancelled
queued / running / validating → invalidated
```

`succeeded`はジョブ処理の成功を表し、モデルの本番採用を意味しない。モデルは `candidate → evaluated → approved → active → retired / invalidated` を別に管理する。

<a id="req-arc-012"></a>

**REQ-ARC-012／P0**：同じ入力・同じidempotency keyでの再要求は、同じジョブを返す。異なる入力への同じkeyは競合エラーにする。

<a id="req-arc-013"></a>

**REQ-ARC-013／P0**：アプリ再起動後に、完了済みジョブが二重で回答やモデルを追加しない。中断ジョブは再開可能か、再実行が必要かを表示する。

## 14. MCP・内部API・データ契約

### 14.1 MCPの提供範囲

C-DNAはMCP serverとして動作し、CodexとClaude Codeの両方から同じ契約を利用できる。両クライアントの公式MCP接続方式を使用する。[S03](#source-s03)[S04](#source-s04)

以下の名称は**C-DNAが新規実装するツール名**であり、既存製品のAPI名ではない。

| ツール | 目的 | 必須scope | 書き込み |
|---|---|---|---|
| `cdna_get_capabilities` | schema版、機能、保管庫状態を取得 | 接続済み | なし |
| `cdna_get_profile` | 許可領域の方針・要約を取得 | `profile:read` | なし |
| `cdna_find_decisions` | 類似する確認済み判断を取得 | `decision:read` | なし |
| `cdna_propose_observation` | 実際の判断の記録候補を登録 | `decision:propose` | 候補のみ |
| `cdna_rank_options` | 状況に対する候補比較 | `judgment:infer` | 監査・任意履歴のみ |
| `cdna_check_policy` | 明示方針の適合を確認 | `policy:read` | なし |
| `cdna_get_learning_gaps` | 不足領域を取得 | `learning:read` | なし |
| `cdna_enqueue_questions` | 学習課題に沿う質問候補を登録 | `question:propose` | 候補のみ |
| `cdna_propose_answer` | 本人回答だとされる内容を確認待ちで登録 | `answer:propose` | 候補のみ |
| `cdna_get_job` | 自分が開始したジョブを照会 | 対象jobの権限 | なし |
| `cdna_cancel_job` | 自分が開始した中断可能jobを停止 | 対象jobの権限 | 状態変更 |

<a id="req-mcp-001"></a>

**REQ-MCP-001／P0**：外部MCPに、本人確認フラグの設定、権限付与、モデル昇格、全保管庫削除、診断同意の変更を公開しない。

<a id="req-mcp-002"></a>

## 16. 自己改善・自己進化の仕様

### 16.1 自己進化の定義

C-DNAにおける自己進化とは、**現在の弱点を診断し、改善案を作り、未使用データで比較し、承認した変更だけを採用する循環**を指す。エージェントが評価指標、権限、本番コードを自由に書き換えることではない。

改善対象を次の五系統に分ける。

| 系統 | 観測すること | 提案すること |
|---|---|---|
| データ品質 | 出典不足、候補未記録、重複、必要条件の欠損 | 確認・補足項目・取り込み規則の改善 |
| 質問品質 | 回答時間、情報不足率、スキップ、誘導の疑い | 問題の短縮、二案比較への切替、背景追加 |
| 学習効率 | 本人の回答時間あたりの性能改善 | 次に聞く領域、質問配分、再確認頻度 |
| モデル品質 | 将来事例での一致、過信、保留、領域別の弱さ | 特徴量・モデル・校正・閾値の比較 |
| 実行性能 | 処理別レイテンシ、メモリ、重複計算 | キャッシュ、batch、モデル軽量化、Mojo化 |

<a id="req-evo-001"></a>

**REQ-EVO-001／P0**：改善案は「問題の観測」「仮説」「変更内容」「検証方法」「予想される副作用」「採用条件」「取り消し方法」を含む。効果の未測定値を確定値として書かない。

<a id="req-evo-002"></a>

**REQ-EVO-002／P0**：改善エージェントが作った質問・説明を、本人の新しい教師データとして自動追加しない。

### 16.2 改善案のデータ契約

```text
ImprovementProposal
  id
  workspace_id
  created_at
  author_kind: local_analyzer | agent | developer_package | human
  target: data | question | model | calibration | runtime
  observed_issue
  evidence_metric_refs[]
  hypothesis
  proposed_change
  expected_direction
  measured_effect: nullable
  evaluation_plan
  required_permissions[]
  privacy_effect
  rollback_plan
  status
  proposal_version
```

`observed_issue`の根拠が集計だけなら、その範囲で説明する。本文を見ずに「本人の価値観を誤解していた」と断定しない。

### 16.3 状態と承認

```text
draft
  → ready_for_review
  → approved_for_experiment
  → evaluated
  → approved_for_activation
  → activated
  → rolled_back / retired

任意の段階 → rejected / invalidated
```

<a id="req-evo-003"></a>

**REQ-EVO-003／P0**：実験の承認と本番反映の承認を分ける。実験の許可だけで現行モデル・質問方針・権限を変更しない。

<a id="req-evo-004"></a>

**REQ-EVO-004／P0**：モデル候補は現行版と同一の入力情報条件で比較する。候補にだけ追加の答えや後日情報を渡さない。

<a id="req-evo-005"></a>

**REQ-EVO-005／P0**：候補が平均一致率を上げても、重要な領域で悪化する場合は自動採用しない。領域別・保留率・負担・速度を併記する。

<a id="req-evo-006"></a>

**REQ-EVO-006／P0**：モデル本番昇格は、署名・schema・特徴量・対象workspace・削除epoch・評価状態・本人承認を確認して、active pointerをatomicに切り替える。

### 16.4 自動化してよい範囲

| 動作 | 初期版の扱い |
|---|---|
| 不足領域の計算 | 自動可能 |
| 改善案の作成 | 許可範囲で自動可能 |
| 現行モデルの横でのshadow評価 | 事前同意・予算内で可能 |
| ローカル候補モデルの学習 | 設定された時間・負荷条件で可能 |
| 本人の方針変更 | 本人確認必須 |
| 別providerへの機密本文送信 | 別の同意必須 |
| 本番モデルの変更 | 本人承認必須 |
| 本番コードの任意改変・実行 | 禁止。通常の署名付き製品更新で行う |
| 評価合格基準の引き下げ | 自動禁止。文書差分と承認が必要 |

GEPAはプロンプト等の最適化候補を作る基盤として検討できる。ただし、最適化器が評価を繰り返し見た結果と、新しい事例に対する性能を区別する。[S30](#source-s30)

<a id="req-evo-007"></a>

**REQ-EVO-007／P0**：GEPA等の最適化器の導入はP1とし、R1では決定的な診断規則＋構造化された改善提案で循環を完成させる。最適化器待ちで基本機能を止めない。

### 16.5 改善画面

改善案一覧は、未確認、実験中、結果あり、採用済みを表示する。各カードに以下を出す。

```text
題名：外注判断に必要な納期情報を補う
観測：確認済み事例の一部で納期情報が未入力
仮説：納期と内製/外注の相互作用を区別できていない可能性
変更：次のヒアリングに納期条件を追加する
本人の負担：追加質問の予定数を表示
外部送信：なし / 対象データを明示
検証：新しい未提示ケースで一致率と情報不足率を比較
結果：未測定
操作：実験を承認 / 保留 / 却下 / 詳細
```

<a id="req-evo-008"></a>

**REQ-EVO-008／P0**：検証前は「改善率」「節約額」「あなたを超えた」等の表示を作らない。既知の測定結果には件数・期間・条件を添える。

**REQ-PRV-001／P0**：この三つを一括チェックボックスにしない。診断共有を拒否しても、C-DNA本体の学習・推論・データ出力を使えるようにする。

<a id="req-prv-002"></a>

**REQ-PRV-002／P0**：「運営者へ本文を送らない」と「端末から何も外へ送らない」を明確に分ける。クラウドLLM利用中に完全ローカルと表示しない。

### 17.2 診断共有の許可リスト

以下は初期の許可候補であり、実装では型・範囲・列挙値を固定する。

| 項目 | 形式 | 制限 |
|---|---|---|
| アプリ版・公式build ID | 公式registry内の値 | 任意文字列を許可しない |
| OS family・CPU class | 粗い列挙値 | ユーザー名、端末名、serialは禁止 |
| メモリ区分 | 8/16/24/32/64GB等のbin | 詳細な端末fingerprintを作らない |
| 処理時間 | 件数と分位点・bucket | タスク本文や時刻の詳細なし |
| エラー種別 | 固定error code | stack trace、path、任意messageなし |
| 学習・入力欠損 | 大分類ごとの集計 | 少数cellを抑制 |
| 評価結果 | 条件・件数・集約指標 | 個々の正解・予測・特徴量なし |
| 診断版 | 固定schema ID | 送信項目が変わる際は再確認 |

**送信禁止の初期リスト**：会話本文、質問本文、備考、顧客名、会社名、氏名、メール、URL、ファイルパス、prompt、embedding、gradient、重み、モデルファイル、原文hash、token、性格回答・尺度得点、細かな取引情報。

<a id="req-prv-003"></a>

**REQ-PRV-003／P0**：allowlist方式にする。禁止語を除去した自由文をそのまま送る方式にしない。未知フィールドは送信前と受信側の両方で拒否する。

<a id="req-prv-004"></a>

**REQ-PRV-004／P0**：モデルや埋め込みに変換したデータを、自動的に匿名化済みと見なさない。R1では診断データとして外部送信しない。

### 17.3 少数データ・識別性

初期設定では、集計cellの元データが20件未満ならそのcellを送信しない。これは製品上の抑制設定であり、匿名性を数学的に保証する値ではない。

同じデータに対する任意の細分化queryや、高頻度の差分取得を許可しない。送信頻度は既定週一回まで、直前プレビュー付きとする。自動送信を選ぶ場合も、期間・項目・停止方法を明示する。

<a id="req-prv-005"></a>

**REQ-PRV-005／P0**：HTTPS受信時にはIP等の通信メタデータが生じることを説明する。「誰のデータか絶対分からない」と保証しない。受信側のアクセスログと診断本文を必要以上に結合しない。

<a id="req-prv-006"></a>

**REQ-PRV-006／P0**：小標本のsuppressionやbinningを、差分プライバシーと呼ばない。差分プライバシーを採用する場合は、隣接関係、clipping、予算、composition、期間を定義する。

OpenDPは差分プライバシーの実装候補となるが、R1の必須基盤にはしない。本人や企業のデータをまたぐ学習は、別の同意・脅威分析・評価を要する。[S36](#source-s36)

### 17.4 ローカル診断エージェント

本文が必要な意味分析は本人端末上で行う。ただしローカルエージェントという名称でも、外部LLMを利用すれば本文が外部に送られるため、送信設定に従う。

ローカルで生成した改善案を開発側へ送る場合は、次のいずれかにする。

1. 固定された課題分類と集計数値だけに変換する。
2. 本人が内容を確認した非機密の再現例を、一件ずつ別操作で共有する。

<a id="req-prv-007"></a>

**REQ-PRV-007／P0**：自由文の「匿名化」をLLMだけに任せ、無確認で送らない。本文を完全に見ない開発側では診断できない問題があることを製品内で明示する。

### 17.5 診断受信API

R1では、ローカルの診断ファイル出力と、任意の運営先へ接続できる最小の受信APIを用意する。クラウド同期や他人の判断を学ぶ共通モデルは含めない。

| endpoint | 用途 | 条件 |
|---|---|---|
| `POST /v1/diagnostics` | 許可済み診断report受領 | HTTPS、schema検証、最大32KiB |
| `DELETE /v1/diagnostics/{receipt_id}` | 受領済みreport削除要求 | 対応する削除token、存在情報の漏えい防止 |
| `GET /v1/improvement-catalog` | 署名済み改善パッケージ一覧 | 一般的な改善情報のみ。保管庫内容を要求しない |

実装はTypeScript等の小さいreceiverでよい。既存の特定インフラや認証システムを前提条件にしない。配置先と保存先はadapter化する。

<a id="req-prv-008"></a>

**REQ-PRV-008／P0**：受信APIは、許可schema、rate制御、期限、保存上限、削除receipt、構造化ログを持つ。未配備ならアプリに「未接続」と表示し、送信済み扱いにしない。

<a id="req-prv-009"></a>

**REQ-PRV-009／P0**：初期の保存方針は受領reportを30日以内、個人と切り離した集約を90日以内とし、実運用で変更する場合は表示と同意を更新する。保存期間を無制限にしない。

<a id="req-prv-010"></a>

**REQ-PRV-010／P0**：開発側から送る改善パッケージは署名された宣言的設定・対応build情報・説明とする。任意コード、SQL、shell、読み取り範囲拡張を実行しない。

### 17.6 将来の連合学習

連合学習、共通事前分布、共有重みはP2とする。導入には、目的、本人同意、勾配・更新値からの漏えい、離脱・削除、評価分布、会社間の価値観衝突を検討する。

<a id="req-prv-011"></a>

**REQ-PRV-011／P0**：R1の共有同意を、将来の共有学習への同意と解釈しない。別のopt-inを必要とする。

<a id="chapter-18"></a>

## 18. セキュリティ・暗号化・削除・復元

### 18.1 脅威モデル

| 脅威 | 防ぐこと | 残る限界 |
|---|---|---|
| 端末紛失・ディスクコピー | 保管庫・モデル・backupの平文漏えい | 解錠済み端末や侵害OSは別 |
| 悪意ある取り込み文書 | prompt injection、path traversal、過大展開 | 本文の事実性まで自動保証しない |
| 不正MCPクライアント | 他workspace、本文、特権更新の取得 | 本人が許可した範囲の持ち出しは制約が必要 |
| 依存・モデルファイル | 任意コード実行、異常メモリ使用 | 上流事故を完全には排除できない |
| 診断機構 | 本文の意図しない外部送信 | 通信metadataの発生は残る |
| 学習の汚染 | AI出力や悪意ある入力による本人モデル変更 | 本人の意図的な誤回答を完全には見破れない |
| 同期・削除の競合 | 削除済みデータが古いjobで復活 | 既に外部へ渡ったコピーは別管理 |

<a id="req-sec-001"></a>

**REQ-SEC-001／P0**：侵害されたOS、同一ユーザー権限のマルウェア、画面録画まで完全に防ぐと説明しない。保護範囲と限界を文書化する。

### 18.2 保管庫暗号化

保管庫ごとに鍵を分け、OSの安全な資格情報保存領域を使用する。macOSではKeychainを使用する。独自暗号を設計しない。

<a id="req-sec-002"></a>

**REQ-SEC-002／P0**：SQLiteのDB本体だけでなく、WAL、関連一時ファイル、検索index、snapshot、モデル、profile cache、backupも保護対象にする。モデルを平文JSONのまま置かない。

<a id="req-sec-003"></a>

**REQ-SEC-003／P0**：鍵、API token、機密本文をcommand line、通常ログ、crash report、analyticsへ出さない。

<a id="req-sec-004"></a>

**REQ-SEC-004／P0**：保管庫ロック時は新規処理を拒否し、進行中処理を停止・隔離し、メモリ上の機密データを可能な範囲で解放する。完全なメモリ消去を検証なしに保証しない。

<a id="req-sec-005"></a>

**REQ-SEC-005／P0**：暗号化・復元の失敗を無言で平文保存へフォールバックさせない。

### 18.3 取り込み・表示の安全性

<a id="req-sec-006"></a>

**REQ-SEC-006／P0**：ZIPのパス外展開、symlink、重複名の上書き、展開爆弾、文字化け、巨大単一messageを検査する。展開先は当該jobの管理領域に限定する。

<a id="req-sec-007"></a>

**REQ-SEC-007／P0**：取り込みHTMLのscript、event handler、外部画像・追跡URLを実行・自動取得しない。必要な情報を安全なテキストへ正規化する。

<a id="req-sec-008"></a>

**REQ-SEC-008／P0**：LLM出力をSQL、正規表現、ルールAST、OSコマンドとして無検査で実行しない。正規表現を許可する場合は計算量とtimeoutを制限する。

### 18.4 訂正・削除の波及

削除対象は、原文だけではない。以下のlineageを追跡する。

```text
Source / Observation / Response
  → normalized representation
  → embedding / retrieval index
  → profile summary / extracted principles
  → training snapshot
  → model / calibration
  → prediction cache / stored explanation
  → pending sharing report / candidate improvement
```

<a id="req-del-001"></a>

**REQ-DEL-001／P0**：`deletion_epoch`を保管庫に持つ。訂正・削除・学習適格性取消しが確定した時点でepochを更新し、すべてのjob・model・cacheの有効性を再判定する。

<a id="req-del-002"></a>

**REQ-DEL-002／P0**：job開始時だけでなく、snapshot出力時、学習結果の受領時、本番昇格時、推論結果の返却直前にepochと権限を確認する。

<a id="req-del-003"></a>

**REQ-DEL-003／P0**：削除対象を使ったモデル・校正・要約を即座に失効させる。再学習完了まで、そのモデルで推論を続けない。利用可能なら残存事例・方針によるモードへ切り替える。

<a id="req-del-004"></a>

**REQ-DEL-004／P0**：削除の代わりに負例を追加するだけでは済ませない。残存する適格データから再生成・再学習する。

<a id="req-del-005"></a>

**REQ-DEL-005／P0**：監査には削除処理の日時・結果・最小IDを残せるが、削除した本文・特徴量・復元可能な内容を永久保存しない。

### 18.5 物理削除の表現

<a id="req-del-006"></a>

**REQ-DEL-006／P0**：SSDやOSのsnapshot、ユーザーが外へ保存したbackupまで確実に物理消去できた、と宣言しない。アプリが管理するファイル削除、鍵破棄、派生物失効、外部送信取消しの各状態を分けて表示する。

<a id="req-del-007"></a>

**REQ-DEL-007／P0**：外部AIや既に共有済みの相手が持つデータについて、アプリ内の削除操作だけで完全消去できるとは説明しない。送信先・受付番号・利用できる削除経路を記録する。

### 18.6 バックアップ・復元・可搬性

| 操作 | 要件 |
|---|---|
| 通常backup | 暗号化。format/schema/build版と整合hashを含む |
| 鍵 | OS機密領域とは別に、本人が管理する復元用保護方式を用意 |
| 復元 | 別保管庫へ試行し、検証成功後に切替。既存保管庫を先に破壊しない |
| export | JSONL＋manifest等の公開形式。機密性を明示して本人操作で開始 |
| partial export | 許可された期間・領域・本文有無を選べる |
| import | 新しいowner確認を経る。外部のtrust flagを信じない |
| migration | 更新前backup、version check、失敗時rollback |

<a id="req-bak-001"></a>

**REQ-BAK-001／P0**：restore後に、現在把握している削除tombstoneと照合して、既に削除済みのデータを自動復活させない。

<a id="req-bak-002"></a>

**REQ-BAK-002／P0**：完全に別の新規端末へ古いoffline backupだけを復元した場合、その後に別端末で行った削除を知れないことを明示する。万能な復活防止を保証しない。

<a id="req-bak-003"></a>

**REQ-BAK-003／P0**：exportした判断データは他製品から読める構造にする。ただしモデル重みだけを渡しても、その版の前処理・方針・適用範囲なしに正しく利用できるとはしない。

<a id="req-bak-004"></a>

**REQ-BAK-004／P0**：backupの復号失敗、改ざん、途中切断、残容量不足で、元データを失わない。

### 18.7 多保管庫・多workspace

R1では端末内に複数のworkspaceを持てるが、本人モデルの共有は既定禁止とする。会社を跨いで再利用する方針は本人が明示的に選び、出典・スコープを変える。

<a id="req-sec-009"></a>

**REQ-SEC-009／P0**：別workspaceのembedding、候補モデル、学習snapshot、会話sessionを使い回さない。共有が承認された定義済み方針のみ別経路で参照する。

<a id="req-sec-010"></a>

**REQ-SEC-010／P0**：権限を狭めたエージェントの会話sessionへ、過去に広い権限で渡した内容が残る場合は、そのsessionを再利用しない。新sessionへ切り替える。

## 19. 性格傾向・価値観・質問票

### 19.1 目的

性格傾向は、本人が自分の傾向を理解し、初期のヒアリングを補助するために用いる。経営能力、倫理性、人格の優劣、医療診断を判定するものではない。

<a id="req-per-001"></a>

**REQ-PER-001／P0**：性格診断を必須オンボーディングにしない。未回答・結果削除でも、判断記憶・比較学習・MCPを使えるようにする。

<a id="req-per-002"></a>

**REQ-PER-002／P0**：会話から推測した性格と、検証された質問票に回答した結果を別の種類として保存する。会話要約を正式な尺度得点へ変換しない。

### 19.2 尺度候補と許諾

| 候補 | 確認内容 | 実装上の判断 |
|---|---|---|
| BFI-2-J | 60項目、5領域、15下位側面。日本語版の検証研究がある | 第一候補。利用条件を確認してから収録 |
| IPIP系 | 原項目・尺度はpublic domainと案内 | 日本語訳の権利・妥当性・採点版を別途確認 |
| HEXACO-PI-R | 6領域。公式は非営利学術利用等の条件を案内 | 商用利用を無条件に前提にしない |

BFI-2-Jの公開説明は構成・検証結果・残る課題を示している。IPIPの原項目の権利と特定の日本語訳の権利は別であり、HEXACOの公開質問票も無条件の商用収録許可とは扱わない。[S31](#source-s31)[S32](#source-s32)[S33](#source-s33)

<a id="req-per-003"></a>

**REQ-PER-003／P0**：R1は結果の手動インポート、由来の表示、削除、アクセス制限までを必須とする。質問票そのものの収録は、利用権と採点仕様が確認できたpackだけを有効にする。

<a id="req-per-004"></a>

**REQ-PER-004／P0**：権利確認が終わっていない尺度を勝手に複製して完成させない。ライセンス未確定でも他のP0経路を止めず、当該尺度を「収録未有効」と表示する。

### 19.3 Instrument pack契約

```text
InstrumentPack
  instrument_id
  version
  locale
  source_reference
  license_reference
  commercial_permission_status
  items_hash
  response_scale
  scoring_rule_version
  reverse_scored_items
  missing_answer_policy
  facet_definitions
  score_ranges
  validation_reference
  scoring_fixture_refs
```

本書は著作権のある質問項目を全文転載しない。実装エージェントが公開ページから勝手に転載することも求めない。

<a id="req-per-005"></a>

**REQ-PER-005／P0**：標準質問票の文言、Likert回答尺度、逆転項目、欠損処理、採点方法を勝手に変えない。左右二値スワイプに変換した場合は元の検証済み尺度と表示しない。

<a id="req-per-006"></a>

**REQ-PER-006／P0**：公式の採点例または許可された検証fixtureで、境界・逆転・欠損・下位尺度・合計を試験する。採点にLLMを使わない。

### 19.4 結果の保存・表示

結果には、尺度ID、版、言語、実施日、入力方法、元の範囲、得点、欠損、出典、本人確認状態を付ける。

<a id="req-per-007"></a>

**REQ-PER-007／P0**：適合する標準化データがない場合、百分位、平均との順位、「上位何％」を生成しない。異なる尺度の得点を無条件に並べて比較しない。

<a id="req-per-008"></a>

**REQ-PER-008／P0**：性格結果から採用・解雇・人事配置・信用判断を自動実行する機能をR1に含めない。Big Fiveの特性を経営者としての優劣へ変換しない。

<a id="req-per-009"></a>

**REQ-PER-009／P0**：性格情報のMCP参照権限と外部送信同意を独立させる。通常の判断プロフィールへの全文混入を避ける。

### 19.5 判断モデルへの入力

性格情報は初期状態では、説明とヒアリング補助だけに使う。学習特徴量として入れる場合は、入れないモデルとのablationを行う。

同一人物の固定した性格値だけでは、その人物の状況ごとに変わる判断を区別できない。そのため、実際の選択、背景、例外条件を置き換えない。

<a id="req-per-010"></a>

**REQ-PER-010／P0**：性格尺度の更新・削除で派生モデルが影響を受ける場合、そのlineageを記録して失効・再学習できるようにする。

### 19.6 価値観ヒアリングは別モジュール

成長と利益、品質と速度、集中と分散、自由度と標準化などのトレードオフを聞く独自の質問は実装できる。ただし、独自質問をBFI-2-Jや検証済み心理検査と呼ばない。

「今の会社で何を優先するか」と「一般的な性格」を分けて、前者には有効期間と背景を持たせる。

## 20. 経営判断・成果改善の境界

### 20.1 本人再現と助言

<a id="req-adv-001"></a>

**REQ-ADV-001／P0**：本人の過去の判断に一致することを、経営成果の最適性と同一視しない。UI・API・評価reportで `imitate` と `advisor` を分ける。

<a id="req-adv-002"></a>

**REQ-ADV-002／P0**：助言モードでは、本人方針との相違、必要な追加根拠、不明点を明示する。助言を自動的に本人の新方針として学習しない。

### 20.2 Outcomeの扱い

成果には、選択時点、観測期間、測定方法、通貨・単位、外部要因、未確定状態を持たせる。受注だけでなく粗利、工数、顧客影響、後悔、方針変更も別に記録できる。

<a id="req-adv-003"></a>

**REQ-ADV-003／P0**：選ばなかった候補の結果を観測したことにしない。選択された施策の売上が高かっただけで、他案より優れていたと断定しない。

<a id="req-adv-004"></a>

**REQ-ADV-004／P0**：R1では、実際の会社に無断の探索施策を実行する強化学習・banditを実装しない。成果最適化の実験には別の承認・制約・検証計画を必要とする。

### 20.3 外部の経営思想

著名な経営者の公開発言・経営思想を取り込む場合は、出典と適用条件を持つ参考方針集として扱う。公開発言だけから本人の全判断を再現できると表示しない。

<a id="req-adv-005"></a>

**REQ-ADV-005／P0**：本人の判断データと、第三者の参考方針を同じ教師ラベルに混ぜない。利用者が参考にする方針を選んだ場合は、その選択自体を本人の方針として確認する。

<a id="req-adv-006"></a>

**REQ-ADV-006／P0**：「世界最高峰」「本人を超える」「必ず成果が上がる」は、比較条件・証拠がない段階では製品の実績表記に使用しない。開発上の志向と、検証済みの性能を分ける。

<a id="chapter-21"></a>

## 21. 評価設計とモデル昇格条件

### 21.1 四種類の評価を混同しない

| 評価 | 問い | 使用データ |
|---|---|---|
| ソフトウェアの正しさ | 契約・数値計算・状態遷移が正しいか | 決定的fixture、境界値、異常入力 |
| 本人の判断再現 | 未学習の背景で本人の選択に合うか | 本人が独立回答した新しいケース |
| 学習体験の効率 | 少ない回答時間で再現範囲が広がるか | 質問時間、出題条件、前後の独立評価 |
| 実務上の成果 | 本人や会社の仕事に役立つか | 実運用・結果・比較条件 |

<a id="req-evl-001"></a>

**REQ-EVL-001／P0**：合成データのfixtureで100%正解しても「本人再現精度100%」と表示しない。ソフトウェア試験と本人データの評価を別reportにする。

### 21.2 比較対象

同一の本人、同一の時点、同一の使用可能情報、同一の候補を使い、次を比較する。

| baseline | 内容 |
|---|---|
| B0 | 明示方針だけ。判定できないときは保留 |
| B1 | 類似する確認済み過去事例の検索 |
| B2 | LLM＋その時点の本人プロフィール。許可される場合のみ |
| B3 | 線形比較モデル＋明示方針＋検索 |
| C1 | LightGBM等の候補モデル＋同じ方針・検索 |
| C2 | 同一モデルのRust／Mojo等のランタイム比較 |

<a id="req-evl-002"></a>

**REQ-EVL-002／P0**：速度比較で、Python側を意図的なfor-loopだけ、Mojo側を最適化batchだけにする等の不公平な比較をしない。Pythonからnative演算を呼ぶ通常の実装を含める。

<a id="req-evl-003"></a>

**REQ-EVL-003／P0**：B2を実行できない場合は理由を記載し、未測定のLLM精度・費用を埋めない。他のbaselineで評価を進める。

### 21.3 指標

| 指標 | 定義・注意 |
|---|---|
| Top-1 agreement | 本人が一つ選んだケースで、モデル一位が一致する割合 |
| Acceptable-set agreement | 本人が許容した集合に推奨が含まれる割合。単一選択と別集計 |
| Pairwise agreement | 本人が比較した二案の順序への一致。tieを分離 |
| Coverage | 評価対象のうち、モデルが保留せず候補を返した割合 |
| Selective error | 保留しなかったケース内での誤り。coverageとセット表示 |
| Calibration | 校正適用範囲内のBrier等。連続scoreに無条件適用しない |
| Information request rate | 情報不足として質問を返した割合 |
| Policy violation | 禁止・承認条件と不整合な表示をした件数 |
| Label efficiency | 本人回答時間に対する、新しい評価集合での改善 |
| Latency / memory | 工程別のp50/p95/p99、peak、cold/warm |
| Burden | 回答時間、スキップ、取り消し、離脱。本人の能力点に変換しない |

<a id="req-evl-004"></a>

**REQ-EVL-004／P0**：分母、件数、期間、対象領域、実例／仮想、モデルの事前提示有無を記載する。件数を伏せた「一致率95%」を出さない。

<a id="req-evl-005"></a>

**REQ-EVL-005／P0**：保留を増やせば一致率が上がることを隠さない。coverageと一致率を同じ画面で表示する。

### 21.4 分割と漏えい防止

<a id="req-evl-006"></a>

**REQ-EVL-006／P0**：原則、過去で学習し、その後のケースで校正・評価する。同じ案件の言い換え、条件差分、同一会話から抽出したケースはfamilyとしてまとめる。

<a id="req-evl-007"></a>

**REQ-EVL-007／P0**：学習、validation、calibration、最終testの用途を区別する。初期配分はデータ量に応じて設計し、少量で無理に分割して意味のない確率を出さない。

<a id="req-evl-008"></a>

**REQ-EVL-008／P0**：検索用記憶、few-shot例、プロフィール、抽出方針、特徴量辞書にも同じ時点制約を適用する。モデル学習だけを分け、プロフィールに未来の答えを含める漏えいを禁止する。

<a id="req-evl-009"></a>

**REQ-EVL-009／P0**：回答後の備考、後日の成果、本人の選択を要約した文章は、同一ケースの予測入力へ入れない。

<a id="req-evl-010"></a>

**REQ-EVL-010／P0**：モデルやエージェントが最終testの正解を繰り返し見た場合、その集合は以後regression用とし、新しい未提示集合で最終評価を行う。

### 21.5 学習データ不足の扱い

初期の数件でも、確認済み事例の検索と明示ルールには価値がある。一方、安定した個人モデルの精度を証明できるまで、検証済みとは表示しない。

| 状態 | 表示例 |
|---|---|
| 記録中心 | 「判断の記録を使えます。まだ予測性能は検証していません」 |
| 学習中 | 「小型モデルを学習しました。独立した確認データが不足しています」 |
| 検証中 | 「○件で確認中。領域ごとの違いがあります」 |
| 適用範囲を限定して検証済み | 「この領域・期間・条件で確認した一致率とcoverage」 |
| 失効 | 「訂正・削除・方針変更により、再検証が必要です」 |

<a id="req-evl-011"></a>

**REQ-EVL-011／P0**：本人に大量回答を強制してから初めて使用可能にしない。未検証状態でも、限界を表示した記憶・ルール・暫定推定を利用できる。

### 21.6 個人モデルの検証目標

次は研究上の保証ではなく、C-DNAが「高い判断再現性を確認した」と表示するための**初期の製品目標案**である。

| 条件 | 初期目標 |
|---|---|
| 独立した新規評価case | 対象スコープで200件以上 |
| 非保留の評価case | 100件以上 |
| Coverage | 60%以上 |
| 非保留のTop-1 agreement | 90%以上 |
| 同agreementの95% Wilson下限 | 85%以上 |
| 方針違反の表示 | 重要な明示方針に対して0件 |
| 評価へのAI回答事前提示 | 主評価ではなし |

平均90%とWilson下限85%は両方満たす必要がある。たとえば100件の非保留だけでは、90件一致しても下限条件を満たすとは限らない。表示範囲の拡大を急がず、不足件数と現在値を示す。

<a id="req-evl-012"></a>

**REQ-EVL-012／P0**：この目標を達成するまで製品全機能の公開を禁止する、という意味にしない。未達の場合は「未検証・限定利用」として公開し、達成済みと宣伝しない。

<a id="req-evl-013"></a>

**REQ-EVL-013／P0**：新モデルの昇格は、適切なpaired評価で現行との差を比較する。初期の許容劣化幅はagreementで2ポイント以内を上限候補とし、95%区間・重要ケース・coverage・負担も確認する。証拠が足りない改善は「改善未確認」とする。

<a id="req-evl-014"></a>

**REQ-EVL-014／P0**：統計的な差が分からないとき、複雑なモデルを優先しない。軽量・単純・説明しやすいモデルを現行維持する判断を許容する。

### 21.7 変化と再評価

価値観・資金状況・事業段階の変化による判断変化は正常な可能性がある。精度低下を検知したら、データ不足、入力変化、方針変更、抽出誤りを分けて調査する。

<a id="req-evl-015"></a>

**REQ-EVL-015／P0**：ドリフトのアラートは「あなたの判断が不安定」ではなく、「以前のモデルとの一致が変わった」と表現し、本人へ背景確認を行う。

<a id="req-evl-016"></a>

**REQ-EVL-016／P0**：再学習しても旧評価を新モデルの実績に転用しない。モデル版・対象期間・校正版を固定して報告する。

## 22. 非機能要件・性能目標・測定方法

### 22.1 性能の基準条件

初期の性能試験は、Apple Silicon・メモリ16GBの実機、release build、CPUだけでも動く構成で行う。正確な機種、OS、CPU/GPU、温度・省電力状態、thread数、build hashを結果に記載する。

負荷fixtureは、10,000件のケース、1ケース最大16候補、構造化特徴最大2,048次元を基準とする。これは製品の絶対上限ではなく、比較条件である。長文生成・新規embeddingは別測定とする。

### 22.2 初期性能目標

すべて未測定の目標値。環境依存性があるため、達成できない場合は測定値と改善案を残す。

| 対象 | 目標 | 含む・含まない |
|---|---|---|
| warm数値スコアリング | p95 ≤ 10ms、p99 ≤ 25ms | 16候補まで。モデル読み込み済み |
| 構造化推論全体 | p95 ≤ 150ms | 認可・ルール・検索・既存特徴・採点。新規LLM/embeddingなし |
| 回答の保存完了 | p95 ≤ 150ms | 入力→永続化→保存済み表示 |
| 確認済み記憶の参照可能化 | p95 ≤ 2秒 | モデル再学習を待たない |
| キー操作の視覚応答 | p95 ≤ 50ms | preloaded card。永続化完了とは別表示 |
| 起動 | p95 ≤ 3秒 | 初回資産取得・本人の解錠時間を除く |
| idle memory | 300MB以内を目標 | UI＋Rust。任意embedding・学習を除く |
| embedding利用時 | 1.5GB以内を目標 | 選定した軽量モデル。超える場合は理由表示 |
| 学習時peak memory | 3GB以内を目標 | 基準fixture、単一candidate |
| 線形の再学習 | 30秒以内を目標 | 基準fixture、固定設定、探索なし |
| LightGBM候補の学習 | 180秒以内を目標 | 一設定。大規模探索全体ではない |

<a id="req-nfr-001"></a>

**REQ-NFR-001／P0**：モデル本体の処理時間を、文章入力からの全体応答時間として表示しない。spanごとのtraceを持つ。

<a id="req-nfr-002"></a>

**REQ-NFR-002／P0**：CPU・メモリを使う学習は、本人が中断・延期できるようにする。バッテリー・省電力・会議中等の条件を設定できるようにし、初期は負荷を控える。

<a id="req-nfr-003"></a>

**REQ-NFR-003／P0**：数値スコアラーの比較はwarm-upを分け、十分な反復、最低3run、p50/p95/p99、memoryを出す。外れ値を勝手に除去しない。

<a id="req-nfr-004"></a>

**REQ-NFR-004／P0**：外部AIを利用した処理は、provider、入力長、出力長、測定時刻、cache条件を記録する。外部サービスのレイテンシをC-DNAが保証する値にしない。

### 22.3 Mojo採用ゲート

| ゲート | 条件 |
|---|---|
| 正しさ | 同じ特徴量・重み・dtypeで参照実装に一致 |
| 数値 | float64比較は初期の許容差abs1e-9、rel1e-8を基準。演算構成に応じて根拠付きで固定 |
| 順位 | 十分なmarginがある候補の逆転なし。近接スコアはtie規則を一致させる |
| 性能 | 実利用で重要な経路の時間を20%以上削減、または現実的なbatch演算で1.5倍以上を確認 |
| 製品品質 | 起動・配布・メモリ・クラッシュ耐性を許容範囲で維持 |
| 保守 | FFI／IPC、compiler、標準ライブラリ更新時の試験がある |

<a id="req-nfr-005"></a>

**REQ-NFR-005／P0**：float32化や量子化で速くなった場合、それを単純な言語差と説明しない。dtype変更は新しいモデルruntime版として校正・順位・精度を再評価する。

<a id="req-nfr-006"></a>

**REQ-NFR-006／P0**：数値同値性の許容差を、失敗が出た後に理由なく広げない。参照実装、丸め、tie、欠損の扱いを先に定める。

### 22.4 信頼性・可用性

<a id="req-nfr-007"></a>

**REQ-NFR-007／P0**：アプリ・Python・Mojo・外部AIのいずれかが停止しても、他の正常な機能に影響を限定する。少なくとも履歴閲覧・export・データ管理の復旧経路を残す。

<a id="req-nfr-008"></a>

**REQ-NFR-008／P0**：DB更新、回答保存、モデル昇格はatomicにする。電源断・クラッシュで半分の回答や壊れたactive modelを残さない。

<a id="req-nfr-009"></a>

**REQ-NFR-009／P0**：本体のoffline基本機能に、ライセンスserverや診断serverへの常時接続を必須にしない。商用ライセンス制御を追加する場合も、本人のデータ出力と削除を妨げない。

### 22.5 アクセシビリティと日本語

<a id="req-nfr-010"></a>

**REQ-NFR-010／P0**：マウスなしで主要操作を完了できる。フォーカス、読み上げラベル、色以外の状態表示、reduced motion、テキスト拡大時の見切れを確認する。

<a id="req-nfr-011"></a>

**REQ-NFR-011／P0**：日本語IME変換中の数字・矢印・Enterを、回答送信として扱わない。備考入力欄、dialog、screen reader利用中のキー競合を試験する。

<a id="req-nfr-012"></a>

**REQ-NFR-012／P0**：日本語と英語の混在、全角半角、金額単位、日時・timezone、絵文字、Unicode正規化を扱う。正規化後も原文出典を失わない。

### 22.6 観測可能性

アプリ内で、非機密のjob ID、状態、時間、エラー分類、モデル版を確認できるようにする。トラブル時の診断ファイルには、共有禁止項目を含めない。

<a id="req-nfr-013"></a>

**REQ-NFR-013／P0**：debug buildでも本文ログを既定offにする。開発時に有効化する場合は、ローカル限定・短期保持・明示表示・テストデータを原則とする。

## 23. 受け入れ試験

### 23.1 試験の原則

以下は最低限必要な受け入れシナリオである。テストファイル数・assert数・coverage値そのものを成果にしない。重複する試験は統合し、重大な失敗モードを確実に検知できる構成を優先する。

実機が必要な試験、認証が必要な試験、本人データが必要な評価を区別する。CIでモックが通っただけで、実接続・署名・精度を確認したと報告しない。

### 24.1 DB制約

| 対象 | 制約 |
|---|---|

### 24.3 回答保存transaction

```text
1. vault unlocked / grant / workspace を確認
2. expected_revision を確認
3. QuestionExposureとCandidate IDを照合
4. 回答schemaを検査
5. 新Observation revisionを保存
6. 旧版の状態とlineageを更新

9. 保存済みイベントをUIへ返す
```

UI表示はtransactionが成功したことを「保存済み」の条件にする。アニメーションの完了を保存完了と見なさない。

<a id="req-db-002"></a>

**REQ-DB-002／P0**：回答が保存されていないのにカードを完全消去しない。失敗時に再送・取消し・備考復元ができるようにする。

### 24.4 学習snapshot

snapshotは適格性判定時点の対象ID・revision・目的・cutoffを固定する。削除されたデータを含むsnapshotを再利用しない。

<a id="req-db-003"></a>

**REQ-DB-003／P0**：snapshotのmanifestだけでなく、実際に入力した各revisionのhashを追跡する。原文の単純hashを外部診断IDとして使用しない。

<a id="req-db-004"></a>

**REQ-DB-004／P0**：既に失効したモデルを参照するcacheがあれば、cache miss扱いにする。推論cacheのkeyにはworkspace、policy、feature、model、epoch、入力hashを含める。

### 24.5 複数ウィンドウ・重複送信

<a id="req-db-005"></a>

**REQ-DB-005／P0**：同じ問いを二つの画面で回答した場合、後の古いrevisionを黙って採用しない。本人に差分を表示する。
