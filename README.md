# C-DNA

[![License: AGPL v3](https://img.shields.io/badge/License-AGPL_v3-blue.svg)](LICENSE)

**日本語** | [English](README.en.md)

**経営者とLLMの対話から判断基準を学び、その成果を小型モデル・記憶・方針へ定着させ、本人の判断を高速に再現する意思決定学習基盤。**

C-DNA が目指すのは「経営者っぽい返答をするチャットボット」ではありません。狙っているのは、**商談中や電話対応中に間に合う速度で、この会社の CEO なら何を選ぶかを、根拠と限界付きで返すこと**です。

> **現在のステータス: 実装・受入検証中。** 暗号化ローカル基盤、学習器、MCPを実装し、既存AIの人物理解を取り込む初期化とLLMとの対話学習を統合しています。公開プレイグラウンドの開発は停止し、エンジンへ集中しています。R1全体・意味表現の蒸留・個人再現精度の受入は未完了です。[起動手順](docs/QUICKSTART.md) / [要件別の検証状況](docs/release/ACCEPTANCE.md)。以下の目標値は達成済みの実測値と区別してください。

# 第I部 — なぜ C-DNA が必要か

## 会社のアイデンティティを決めるのは、CEO の判断である

商品を何にするか、どの案件を断るか、品質と納期のどちらを取るか。会社のアイデンティティは、こうした一つ一つの判断の積み重ねで決まります。決めているのは CEO です。

問題は、その判断が**必要な場所と必要な時刻に存在しない**ことです。

会社が大きくなるほど、CEO 本人が判断に関われる割合は下がります。CEO 自身に時間がない日もあります。そして現場には、判断速度そのものを要求される場面があります。

## しかし、その判断は枝の先まで届かない

- **営業中に、営業マンが CEO のアイデンティティを発揮することはできません。**目の前で条件を詰めている最中に、CEO の判断基準を思い出して正しく適用することは現実的ではありません。
- **クレーム対応の電話中に、コールセンターが CEO のアイデンティティを発揮することはできません。**相手は待ってくれません。

枝の先の先までアイデンティティが行き届かないからこそ、理念浸透の研修や、それに準ずる活動が必須になります。

そして、その前提は崩れつつあります。**これからの時代、人材は非常に流動的になっていきます。**数年かけて理念を浸透させる前に、人は入れ替わります。

だから必要なのは、次の状態です。

> **今日入ってきた人でも、CEO のアイデンティティが行き届いている。**

## 既存の選択肢は、どちらも現場で中途半端になる

ルール、LLM、小型の判断モデルには異なる役割があります。C-DNAはLLMによる深い対話を学習の中心に据え、その成果を繰り返し使う場面の応答時間と本人再現精度を測ります。以下は設計上の役割比較であり、競合製品の実測順位ではありません。

| 観点 | ルールベース判定エンジン | LLM | C-DNA |
| --- | --- | --- | --- |
| **応答速度** | 定義済み条件を直接評価 | モデル・入力・接続条件による | 学習成果をローカルで再利用し、入力から回答まで測定する(→[速度目標](#速度目標)) |
| **判断の精度** | 定義したルールと適用範囲による | モデル・本人の文脈・課題による | 本人の選択との一致率と回答範囲を測り、未検証領域は質問・保留へ回す |
| **条件の組み合わせ** | 弱い。組み合わせが増えるたびにルールを足す必要がある | 強い | 「納期が短い × 外注」のように背景と選択肢の組み合わせを学ぶ |
| **立ち上げの手間** | ルールの定義・保守 | 既存の会話・記憶を利用できる場合がある | 専用プロンプトで既存AIの理解を取り込み、不足だけを対話で補う |
| **実行コスト** | ルール数・実行環境による | モデル・契約・呼出量による | 学習時のLLM費用と判断時の処理費用を分けて最適化する |
| **判断の根拠** | どのルールに当たったか | 生成された文章。根拠は事後的な説明になりやすい | 過去の本人判断・状況・例外条件を出典付きで返す |
| **誰の判断か** | ルールの出典による | 与えた本人情報・会話・指示による | **この会社の CEO の判断との一致を独立評価する** |

LLMは、本人がまだ言語化できていない基準を仮説にし、理由・反例・逆転条件を質問する役割を担います。本人の訂正を受けて表現と学習方針を改善し、独立した本人回答で確かめた成果を判断基盤へ定着させます。

## ちょうどいい塩梅の判断アルゴリズムが、なかった

これが C-DNA の出発点です。

狙いは、**「この会社の CEO の判断を、現場の速度で返す」**ことです。

学習中はLLMを使って理解を深め、判断時は学習済み表現・小型モデル・記憶を再利用します。新しい文章や未知の概念には追加の理解処理が必要です。その時間も含めて測り、構造化済み候補の採点時間だけで高速性を主張しません(→[全体構成](#全体構成))。

## 座学で覚えるのではなく、判断を通して覚える

LLM は巨大なので、CEO の判断根拠を長い文章として読み、**座学で学ぶ**ことはできます。しかし、それを学んでいる時間帯、現場の人間は常に認知負荷が高い状態に置かれます。これは**人材の疲弊**に直結します。

C-DNA が取るのは逆の順序です。**現場の判断を通して、経営者の傾向を瞬時に学んでいきます。**

実際に学習定着率が高いのは、座学で学ぶときよりも、**実際に体験するとき**です。C-DNA を使うと、この非対称が両方向に効きます。

| | C-DNA を通して得られるもの |
| --- | --- |
| **経営者** | 言語化できていなかった自分の判断ロジックを、自分で学ぶことができる |
| **現場** | CEO の判断を座学で暗記するのではなく、実際の判断として体験できる |

結果として成立するのは、次の二つです。

> **CEO は、判断をクローンできる。**
> **現場は、CEO の判断をそのまま使える。**

この体験を支えるのが、本人とLLMが判断の違いを確かめ、その成果を更新し続ける学習循環です。

## C-DNA が返すもの

「本人らしい」と「経営上よい」は、同じ評価指標ではありません。混ぜると、どちらの用途にも使えなくなります。そのため C-DNA の出力は最初から三つに分かれています。

| モード | 返すもの |
| --- | --- |
| **本人再現** | 「今のあなたなら、こちらを選ぶ可能性が高い」 |
| **改善提案** | 「あなたの好みとは違うが、この条件では検討すべき選択肢がある」 |
| **保留・質問** | 「この情報がないと判断を再現できない」 |

三番目が重要です。**判断材料が足りないときに黙って答えを出さないこと**を、精度と同じ重みで扱います。

# 第II部 — どう作るか

## 全体構成

中心となるのは、**CEO ↔ LLM ↔ 学習エンジン**の循環です。LLMは学習時に深く対話し、Pythonは確認された判断から表現と小型モデルを学習・評価し、Rust／Mojoはその成果で高速に判断します。工程の分離は速度と権限を管理するためであり、LLMを学習から外すためではありません。

初回は専用プロンプトを普段のChatGPT／Claudeへ渡し、参照できる本人情報を構造化して取り込みます。本人が訂正し、LLMが重要な不足や例外を追加質問します。初期実装の17特徴量は比較用の基準であり、本人独自の概念を捨てる恒久的な上限ではありません。

```text
専用プロンプト → ChatGPT / Claude の判断傾向・例外
会話エクスポート / 本人の訂正
Codex / Claude Code での実際の判断
C-DNA アプリでの四択・比較・備考
                    ↓
          判断候補の抽出・構造化
                    ↓
       出典確認 / 重複除去 / 本人確認
                    ↓
       ローカルの判断データベース
                    ↕
       CEO ↔ LLM：理由・反例・逆転条件
       次の質問 / 意味表現・学習改善の仮説
                    ↓
       ┌────────────┴─────────────┐
       ↓                          ↓
 判断記憶・明示ルール          学習・独立評価
 すぐに反映                   Python
       ↓                          ↓
 類似事例の検索             版付き表現＋小型モデル
       └────────────┬─────────────┘
                    ↓
         Rust 中心の高速判断基盤
         必要な数値演算は Mojo
                    ↓
       候補比較 / 根拠 / 不足情報
       判断を控えるべきかの判定
                    ↓
       C-DNA / Codex / Claude Code
       などの実務エージェントから利用
```

外部エージェントとの接続は MCP サーバーを共通入口にします。C-DNA 側が公開するツールは、判断方針の取得、過去判断の検索、判断候補の登録、選択の予測、学習が薄い領域の取得、回答の登録です。**エージェントが自由に「本人確認済み」と設定できる設計にはしません。**本人確認は、アプリ操作など信頼できる入力経路に紐付けます。

## 何を学ぶのか

「経営者の DNA」を一つのデータに押し込むと、性格・会社の状況・経営方針が混ざります。同じ人でも、手元資金が潤沢なときと資金繰りを優先するときでは判断が変わります。それを性格の変化と誤解するモデルは作りたくありません。

そこで、次の六層に分けて保持します。

| 層 | 保持するもの | 例 |
| --- | --- | --- |
| **性格傾向** | 比較的安定した行動傾向 | 新しいことへの関心、慎重さ、計画性 |
| **価値観・優先順位** | 何を重視するか | 成長、利益、時間、品質、信用、自由度 |
| **明示的な経営方針** | 本人が承認した方針・制約 | 特定条件では受注しない、一定額以上は本人承認 |
| **会社・案件の状況** | 判断時点の条件 | 資金、人数、納期、事業段階、既存顧客への影響 |
| **実際の選好** | この状況なら何を選ぶか | 内製より外注、短期売上より継続性 |
| **結果と振り返り** | 選んだ結果、どうなったか | 利益、工数、失敗、後悔、判断基準の変更 |

**主役は「実際の選好」です。性格診断はその補助情報にすぎません。**開放性が高いから事業投資を承認する、という推論は成り立ちません。性格プロフィールがほぼ固定なら、それだけでは日々変わる条件の違いを説明できないからです。

## 判断一件のデータ設計

C-DNA の強さは、大量の文章を保存することではなく、**「なぜその状況で、その候補を選んだのか」を比較可能な形で残すこと**にあります。判断一件には、状況・目的・制約・選択肢・選択結果・本人の明示理由・出典と確認状態を持たせます。

特に、次の三つを必ず残します。

**何が変われば判断が逆になるか。** 「外注を選ぶ」という答えだけでは弱いです。「今回は納期が重要だから外注。納期が長く、社内資産化が目的なら内製」まで分かると、判断の境界を学べます。

**その判断の前に AI の提案を見ていたか。** 本人が独立して選んだのか、AI に勧められた後で採用したのかを分けます。どちらも有用ですが、同じ観測ではありません。

**当時は分からなかったこと。** 後から判明した売上や失敗を、当時の判断材料に混ぜません。結果を知った後の説明を学習し、未来の判断が当たるように見せてしまう事故を防ぐためです。

## 学習は三段階に分ける

回答ごとに全部を再学習する必要はありません。**「すぐ覚えること」と「モデルの重みをすぐ変えること」は、同じではありません。**

| 段階 | 回答後に行うこと | 目的 |
| --- | --- | --- |
| **即時反映** | 判断記憶・承認済み方針に追加 | 直後から同じ判断を参照できる |
| **軽量更新** | 小型比較モデルを追加学習 | 少ない処理で選好を更新する |
| **再評価付き更新** | 蓄積データで強いモデルを再学習 | 品質を確認して本番モデルを更新する |

一件答えた直後に「同じ条件では、本人がこちらを選んだ記録があります」と返せるだけでも、すでに学習効果があります。記憶への反映は速く、モデルの本番昇格は慎重に行います。

なお、判断モデルは**四クラス分類器にしません。**問題ごとに選択肢 A の意味が違うからです。学ぶのは「状況と選択肢の内容から、その選択肢を本人が好む度合い」を返す関数です。初期は正則化した比較モデル、データが増えたら候補ランキングモデルへ進みます。

## 技術スタック

| 領域 | 採用 | 役割 |
| --- | --- | --- |
| **学習** | Python(scikit-learn / LightGBM / Polars) | 小型比較モデル、ランキングモデル、判断データの整形と評価 |
| **アプリ・データ・推論制御** | Rust(Tauri / rusqlite / MCP SDK / ONNX Runtime ラッパー) | PC アプリ、ローカル判断 DB、MCP サーバー、推論の実行 |
| **数値計算の高速化** | Mojo | 特徴量変換、複数候補の一括採点、類似度計算など効果が出る部分のみ |
| **環境管理・データ契約** | uv / Pydantic | Python 環境の固定、判断イベントと API のスキーマ定義 |

最初から全部を Mojo に寄せるのではなく、既存ライブラリで判断モデルの品質を確立し、そのモデルを高速化する順序を取ります。**Python で学習した任意のモデルをそのまま自動で Mojo へ変換できる、という前提は置きません。**

そのため推論側には交換可能な共通契約(`DecisionScorer`)を置き、Rust の小型スコアラー・ネイティブ木モデル推論・ONNX Runtime・Mojo を差し替えて比較できるようにします。**C-DNA の価値を Mojo の採用可否に依存させません。**Mojo は Mac と Linux をネイティブに対応し、Windows は WSL 経由のため、Mojo が動かない環境でも Rust 側の標準推論で使える状態を維持します。

## 速度目標

初期の設計目標は次のとおりです。

> **構造化済み入力・モデル読み込み済み・ローカル実行において、数個〜数十個の候補比較を p95 で 10ms 以内。**

**これは未計測の目標値です。**そして、以下は目標に含めず、別々に計測します。

| 工程 | 別に測る理由 |
| --- | --- |
| 新規文章の解析 | LLM と文章量の影響を受ける |
| 埋め込み生成 | モデルと入力長の影響を受ける |
| DB 読み込み・通信 | 数値演算とは別の待ち時間 |
| 候補スコアリング | Rust / Mojo などの比較対象 |
| 説明文の生成 | 生成 LLM を使う場合は別の速度特性 |

**「モデル本体だけ 1ms でした」を、アプリ全体の判断速度として提示しません。**

## 何をもって「精度が高い」と言うか

一つの「精度」だけを見ると危険です。C-DNA では次を分けて評価します。

- **本人との判断一致** — 未学習の状況で、本人の選択をどれだけ再現できるか
- **許容候補の再現** — 本人が許容する複数候補を取りこぼしていないか
- **過信の少なさ** — 自信が高いと言った場面で、実際に一致するか
- **判断保留の適切さ** — 情報不足・未知領域で無理に答えていないか
- **再現できる範囲** — 高い一致率を保ったまま、どれだけの場面を扱えるか
- **本人の負担** — 学習に使った時間に対して、どれだけ改善したか
- **速度・資源消費** — 入力処理から出力までの待ち時間、メモリ、CPU

比較対象には、少なくとも「明示ルールだけ」「類似する過去判断の検索だけ」「LLM + 本人プロフィール」「C-DNA の小型モデル」を並べます。評価データは、過去で学習して未来で評価し、同じ案件の言い換えを学習側と評価側に分散させません。

また、四択で本人の選択を当てられたとしても、「その選択が、選ばなかった案より利益を生んだ」とはまだ言えません。**成果データを貯めることと、因果的に優れた判断を特定することを分けます。**

## プライバシー

**経営判断の本文を、運営側が見ない**前提で設計します。中身の分析はユーザー端末で行い、外へ出すのは許可された診断結果だけにします。

| データ | 初期設定 |
| --- | --- |
| 会話本文・備考・会社名・顧客名 | 送信しない |
| 過去の判断の原文 | 送信しない |
| 埋め込みベクトル・モデル重み・勾配 | 送信しない |
| 処理時間・メモリ使用量・エラー種別 | 同意があれば共有 |
| 学習件数・入力不足率・大分類ごとの評価 | 少数ケースを抑制して共有 |

**「ベクトルなら匿名」「学習済みモデルなら安全」とは扱いません。**データ共有を止めても本体機能は使えるようにします。また、ローカル保存のアプリであっても、クラウド LLM に本文を渡せばその処理は外部で行われます。**「運営側に送らない」と「一切外部へ出ない」は、別の設定として扱います。**

## ロードマップ

| 段階 | 完成させる範囲 |
| --- | --- |
| **1. 判断を集め、根拠付きで使える** | 要約インポート → 本人確認 → 四択・比較・備考 → ローカル保存 → MCP で参照・登録。学習モデルの完成を待たずに、過去の判断を引ける製品にする |
| **2. 実際に学習し、足りない部分を聞ける** | 小型比較モデルの導入とランキングモデルとの比較。学習が薄い領域を検出して質問し、未使用事例での再現率が改善することを検証する |
| **3. 速さと配布品質を完成させる** | 推論を Rust 側で扱い、計測結果に応じて Mojo を追加。同じ入力・同じモデルから、実装をまたいで同じスコアと保留判断が出ることを確認する |
| **4. プライバシーを保った改善ループ** | ローカル診断、改善提案、共有内容のプレビュー、同意に基づく指標共有、候補モデルの承認付き更新 |

段階 2 が、**「育てると判断が変わる」体験を測定可能な形で完成させる地点**です。

## この先、C-DNA で独自に作る価値がある部分

機械学習そのもの、ローカル推論、MCP、PC アプリの基盤は、既存ライブラリからかなり借りられます。自分たちで作るべき中心は、次の三つです。

1. **本人の判断を、出典・背景・例外条件付きで蓄積するデータモデル。**
2. **少ない回答時間で判断の穴を埋める、質問・比較・再確認の仕組み。**
3. **根拠と限界を返しながら、既存エージェントから使える高速な判断インターフェース。**

この三つが揃えば、C-DNA は「経営者の分身チャット」ではなくなります。

**ChatGPT や Claude で考える。Codex や Claude Code で実行する。その途中で現れた本人の判断を C-DNA が学び、次の仕事では本人が毎回説明しなくても、その方針を使える。**

この循環が、C-DNA の目指す完成形です。
